# MewCode 第五章规格说明：Prompt 工程与缓存管线

## 背景
第四章完成 Agent Loop 后，MewCode 已经可以连续调用模型和工具，自主完成多步任务。但当前提示词仍然比较原始：正常模式缺少统一的全局行为约束，Plan Mode 依赖把一段说明拼进用户消息，工具描述也只提供了基础用途说明。

这种做法在早期可用，但会带来几个问题：模型行为不稳定，模式指令和用户意图混在一起，环境信息容易污染可缓存内容，Prompt Cache 难以命中，工具选择习惯也无法被系统性塑造。第五章要把提示词从零散字符串升级为一套可维护、可扩展、可评估的 Prompt 工程体系。

## 目标用户
- 希望 MewCode 在普通编码任务中表现更稳定的开发者。
- 希望 Plan Mode 更像成熟 Coding Agent 规划模式的用户。
- 正在学习 Agent Prompt 分层、动态注入和 Prompt Cache 策略的开发者。
- 后续要扩展项目指令、记忆系统或 MCP 能力的实现者。

## 阶段目标
本阶段要交付一套 Provider-aware Prompt 组装管线。MewCode 的全局指令按职责拆成七个稳定模块，并按优先级组合；环境上下文、会话历史、模式提醒和工具定义按来源分发到 API 的不同通道。稳定内容保持稳定前缀并附带缓存策略，变化内容进入消息通道，Plan Mode 通过 system-reminder 动态注入，不再拼接到用户输入或污染稳定提示词。

本阶段同时强化内置工具描述，让模型更清楚什么时候使用专用工具，什么时候避免通用命令，以及编辑前后应如何配合读取、修改和验证。完成后，MewCode 应能通过 API 返回的 usage 信息观察 Prompt Cache 是否命中或明确知道当前 Provider 不支持相关观测，并能用典型场景脚本对提示词行为做人工对照评估。

## 能力清单
- MewCode 拥有七模块 System Prompt 结构。
- 每个 System Prompt 模块都有名称、内容和优先级。
- System Prompt 可以按优先级稳定排序并拼装。
- 身份模块定义 MewCode 的角色、边界和协作方式。
- 行为模块定义理解任务、主动推进、必要时澄清和保持上下文一致的原则。
- 工具使用模块定义优先使用专用工具、按需读取、执行后观察结果的规则。
- 代码质量模块定义小步修改、遵循项目风格、验证改动和避免无关重构的原则。
- 安全边界模块定义对破坏性操作、敏感信息和不可确认行为的约束。
- 任务模式模块定义普通编码任务、解释任务、排查任务和计划任务的行为差异。
- 输出风格模块定义默认回复语言、Markdown 展示和最终总结格式。
- Prompt 组装管线可以把七类输入源分发到 system、messages 和 tools 三个 API 通道。
- 环境上下文作为对话消息注入，而不是拼入全局 System Prompt。
- system-reminder 可以用特殊标签承载运行中的补充指令。
- system-reminder 支持会话级提醒和轮次级提醒。
- Plan Mode 指令通过请求时 system-reminder overlay 注入。
- Plan Mode 按模型请求轮计数，首轮使用完整提醒，后续按节奏重复完整提醒，其余轮次使用精简提醒。
- Plan Mode 默认在聊天中输出计划，不自动写入计划文件。
- 工具描述补齐用途、优先级、配合关系和注意事项。
- Provider 可以保留或暴露 API 返回的 token usage 与缓存命中信息。
- Provider-aware 缓存策略可以通过 usage 信息被验证。
- 项目提供一组典型场景，用于人工比较提示词改动前后的行为差异。

## 非功能要求
- 稳定提示词内容应尽量保持稳定顺序，避免无意义变动破坏缓存。
- 动态环境信息不能进入可缓存的全局指令通道。
- system-reminder 应被模型理解为系统级补充，而不是用户请求的一部分。
- Plan Mode 不应因为模式提醒变化导致稳定全局指令频繁失去缓存价值。
- 工具描述应足够明确，但不能长到压垮上下文预算。
- 提示词模块应便于后续章节插入项目指令、记忆和 MCP 相关内容。
- 缓存命中验证应可观测，不能只停留在代码结构假设。
- 评估脚本应服务于人工判断，不要求本章实现自动打分系统。

## 设计骨架
MewCode 第五章按以下层次组织：

1. System Prompt 模块层
   - 负责定义七类稳定全局指令。
   - 负责为每个模块保存身份、内容和优先级。
   - 负责生成稳定、可缓存的系统提示词文本。

2. Prompt 组装管线层
   - 负责收集全局指令、工具定义、环境上下文、会话历史、当前用户输入、工具调用结果和模式提醒。
   - 负责把不同来源的信息分发到 system、messages 和 tools 通道。
   - 负责用统一中间结构表达 cache policy，再交给 Provider 翻译为各自 API 能力。

3. 环境上下文层
   - 负责收集当前工作目录、平台、时间、Git 状态等动态信息。
   - 负责把环境信息作为首条系统级补充消息注入请求。
   - 负责避免动态环境内容影响全局提示词缓存。

4. system-reminder 层
   - 负责把运行时补充指令包装成特殊标签消息。
   - 负责区分会话级提醒和轮次级提醒。
   - 负责支持模式切换、外部能力上线和温和行为提醒。
   - 负责以请求时 overlay 形式参与组装，不污染持久会话历史。

5. Plan Mode 提示层
   - 负责提供 Plan Mode 的完整提醒和精简提醒。
   - 负责按模型请求轮控制提醒注入频率。
   - 负责替代第四章中拼接用户消息的 Plan Mode 实现。
   - 负责默认在聊天中产出计划，只在用户明确要求时写入计划文件。

6. 工具描述层
   - 负责强化内置工具说明。
   - 负责说明工具之间的配合顺序。
   - 负责让模型减少错误工具选择。

7. 缓存观测层
   - 负责从 Provider 响应中提取 token usage 和缓存命中信息。
   - 负责把缓存数据暴露给调试输出或测试断言。
   - 负责支持后续优化提示词长度和分层策略。

8. 评估场景层
   - 负责提供典型提示词行为场景。
   - 负责让开发者手动对照模型是否按预期使用工具、规划和输出。

## 七源到三通道分发原则
- 稳定身份、行为规则、代码规范、安全边界和输出风格进入 system 通道。
- 工具名称、参数、用途、优先级和配合关系进入 tools 通道。
- 动态环境信息进入 messages 通道。
- 历史用户消息和历史 assistant 最终回复进入 messages 通道。
- 当前用户输入进入 messages 通道。
- 工具调用历史和工具结果进入 messages 通道。
- 模式提醒、运行时补充指令和临时限制通过 system-reminder 进入 messages 通道。
- 会话级 system-reminder 注入在会话早期，轮次级 system-reminder 注入在当前用户请求附近。
- 不把当前时间、Git 状态、工作目录等高频变化信息拼入 System Prompt。
- 环境上下文和 system-reminder 默认只参与请求时组装，不作为真实对话历史永久保存。

## Plan Mode 行为边界
- Plan Mode 是会话级模式开关，但提示词注入按轮次控制。
- Plan Mode 轮次按 Agent Loop 内部模型请求计数，而不是按用户消息计数。
- Plan Mode 下模型应优先澄清大型或含糊需求。
- Plan Mode 下模型可以使用只读工具理解项目。
- Plan Mode 下模型默认在聊天中产出计划。
- Plan Mode 下只有用户明确要求保存计划文件时，模型才可以产出计划文档文件。
- Plan Mode 下模型不应修改源码、运行命令或执行实现步骤。
- Plan Mode 的约束仍由工具执行层兜底，提示词只负责引导模型减少错误调用。

## 缓存策略边界
- 本章只实现 Provider 原生能力可支持的 Prompt Cache 控制和观测。
- Prompt 管线只表达统一 cache policy，不直接假设所有 Provider 都支持相同缓存字段。
- 支持显式缓存控制的 Provider 应把稳定 system 和 tools 内容翻译为对应 API 的缓存控制。
- 支持自动 Prompt Caching 的 Provider 应保持稳定前缀，并读取对应 usage 字段观察命中。
- 不支持缓存的 Provider 应保持功能可用，并以空 usage、零命中或不支持状态表现。
- 缓存命中受模型、token 门槛、请求间隔和供应商策略影响，本章不承诺每次请求都能命中。
- 缓存命中只作为成本优化目标，不作为 Agent 正确性的唯一依据。

## Out of Scope
- 不加载项目级指令文件。
- 不实现自动记忆系统。
- 不接入真实 MCP Server。
- 不实现自动评估打分。
- 不实现多语言 Prompt 模板市场。
- 不实现用户自定义 Prompt 编辑器。
- 不实现上下文压缩。
- 不改变第四章 Agent Loop 的核心循环语义。
- 不引入完整权限系统。

## 完成定义
当 MewCode 能用七模块 System Prompt 生成稳定全局指令，把七类输入源正确分发到 system、messages 和 tools 三通道，并且 Plan Mode 不再通过拼接用户消息生效时，本章达到核心完成标准。验收还需要证明：工具描述被强化，Provider-aware 缓存策略和 usage 观测存在，Plan Mode 的完整与精简提醒按模型请求轮注入，典型场景脚本可以帮助人工比较提示词行为。
